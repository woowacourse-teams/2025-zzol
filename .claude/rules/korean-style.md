## 한국어 문체 규칙

이슈·PR·리뷰 코멘트가 사람이 쓴 글로 읽히게 하는 규칙이다. 한국어를 모국어로 쓰는 개발자가 직접 쓴 것처럼 적는다. 짧게 쓰는 것보다 한 번 읽고 뜻이 들어오는 쪽을 우선한다.

### 적용 대상

GitHub 이슈 본문, PR 제목과 본문, 리뷰 코멘트와 답글, 커밋 메시지, 저장소 안의 한국어 문서와 주석.

본문 **구조**는 [create-pr](../skills/create-pr/SKILL.md)이 정한다. 무엇이 달라지는지부터 쓰는 순서, 정보 결합도, mermaid 사용 기준이 거기 있다. 이 문서는 **문장과 낱말**만 다룬다.

### 문장

- 한 문장에 핵심 하나만 담는다. 새로운 판단이나 근거, 조건이 나오면 문장을 나눈다.
- 결론을 문장 앞에 둔다.
- 주어와 서술어를 멀리 떼어놓지 않는다.
- 같은 말을 표현만 바꿔 되풀이하지 않는다.
- 뜻이 흐린 추상어 대신 무엇이 어떻게 달라지는지 적는다.

모든 문장을 짧게 끊으라는 말은 아니다. 하나의 주장을 설명하는 조건이나 보충은 같은 문장에 남긴다.

### 쓰지 않는 표현

**번역투 연결어.** 대개 조사나 동사로 바꾸면 짧고 자연스러워진다.

| 쓰지 않는다 | 대신 |
| --- | --- |
| ~을 통해, 이를 통해 | ~로, ~해서, 그래서 |
| ~함으로써 | ~해서, ~하면 |
| ~를 기반으로, 이를 바탕으로 | ~로, ~를 써서 |
| ~에 있어서, ~하는 데 있어 | ~에서, ~할 때 |
| ~할 수 있도록 | ~하게, ~하려고 |
| 이러한, 다음과 같은 | 이, 그, 위, 아래 |

**내용 없는 부사.** 지우거나 잴 수 있는 말로 바꾼다.

효율적으로 · 안정적으로 · 유연하게 · 효과적으로 · 종합적으로 · 체계적으로 · 궁극적으로

> ❌ 캐시를 도입해 조회 성능을 효율적으로 개선했다.
> ✅ 캐시를 도입해 방 조회 쿼리를 요청당 3회에서 0회로 줄였다.

정확히 그 뜻일 때는 써도 된다. 다른 말로 바꿀 수 있으면 바꾼다.

### 하이픈

문장 안에서 하이픈으로 정보를 잇지 않는다. 읽는 사람이 관계를 직접 추측해야 한다.

> ❌ Redis Stream 도입 - 메시지 유실 방지 - 처리 순서 보장
> ✅ Redis Stream을 도입해 메시지 유실을 막고 처리 순서를 보장했다.

> ❌ 문제-원인-해결 방법
> ✅ 문제의 원인을 찾고 해결 방법을 정리했다

실제로 목록인 내용은 Markdown bullet으로 적는다. 문장을 짧아 보이게 하려고 bullet으로 쪼개지 않는다.

### 괄호

본문에 넣어도 되는 설명을 괄호에 넣지 않는다.

> ❌ Redis Stream(메시지 처리 시스템)을 도입했다.
> ✅ 메시지 처리 시스템인 Redis Stream을 도입했다.

괄호는 버전·약어·단위·이슈 번호처럼 본문과 떼어야 뜻이 분명해지는 정보에만 쓴다. 예: `(#1404)`, `(Java 21)`.

### 문단

한 문단에 주장 하나만 담는다. 순서는 문제, 판단, 행동, 결과로 잡는다.

작업 목록만 늘어놓지 않는다. 왜 그 작업을 했는지가 드러나야 한다.

### 내보내기 전 점검

이슈·PR·코멘트를 올리기 전에 아래를 하나씩 짚는다. 통과하지 못한 항목이 있으면 그 문장을 다시 쓴다.

- [ ] 문단마다 첫 문장만 읽어도 핵심을 알 수 있다
- [ ] 한 문장에 서로 다른 내용이 섞여 있지 않다
- [ ] 위 표의 번역투 연결어가 남아 있지 않다
- [ ] 내용 없는 부사를 지웠거나 잴 수 있는 말로 바꿨다
- [ ] 문장 안에서 하이픈으로 정보를 잇지 않았다
- [ ] 괄호를 지워도 뜻이 통한다
- [ ] 같은 뜻을 표현만 바꿔 반복하지 않았다
- [ ] 소리 내어 읽었을 때 걸리는 문장이 없다

괄호나 하이픈에 걸렸으면 문장을 줄이지 말고 정보를 나눈다.
