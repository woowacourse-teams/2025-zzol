# retro — 회고

작업에서 배운 것을 규칙·도구로 내리는 절차. **산출물은 "느낀 점"이 아니라 저장소의 변경**이다 — 규칙 갱신, 도구·스킬 추가, 또는 규칙 삭제. 아무것도 안 고칠 거면 회고를 돌리지 않는다.

## 언제 돌리나 — merge 후가 아니라 리뷰 반영 직후

[issue-workflow](../../rules/issue-workflow.md) 5단계(리뷰 반영)를 마친 **그 세션 안에서** 돌린다.

merge 시점이 아닌 이유: 이 저장소는 merge를 사용자가 한다([git-push-safety](../../rules/git-push-safety.md) merge 권한). Claude 세션은 리뷰 반영에서 끝나고 merge는 그 뒤 다른 시점이라, merge 후에 회고하면 **아래 1-3 수집(개입)이 통째로 빈다** — 트랜스크립트가 남의 세션이거나 없다. 지적·재작업·개입이 한 세션 안에 다 있는 마지막 순간이 리뷰 반영 직후다.

## 1. 수집

세 갈래를 모은다. **셋 다 비면 회고를 억지로 만들지 않고 끝낸다.**

### 1-1. 리뷰 지적 중 반영된 것

```bash
PR=${1:-$(gh pr view --json number -q .number)}
gh pr view "$PR" --comments          # deep-review 코멘트 + 사람 코멘트
```

미해결 스레드가 아니라 **반영한 것**을 본다 — 반려한 지적은 규칙 후보가 아니다. 스레드 목록은 issue-workflow 5단계의 GraphQL 쿼리를 쓴다.

### 1-2. 재작업한 커밋

```bash
git log --oneline origin/dev..HEAD
```

같은 파일을 두 번 이상 고친 커밋, "수정"·"보완"·"누락" 류 메시지가 재작업 신호다. 한 번에 맞았으면 배울 게 없다.

### 1-3. 사용자 개입 — 이게 규칙의 최대 원천이다

산출물에는 안 남고 대화에만 남는다. **같은 말을 두 번 들었다**(지시가 있는데 안 지켜졌다는 뜻이라, 강조를 더할 게 아니라 도구로 내릴 신호다), **사용자가 직접 해버렸다**(스킬 갭), 하겠다고 해놓고 안 한 것, 앞뒤가 어긋난 판단.

**자기 세션을 자기가 읽으면 의도를 이미 알아서 구멍이 안 보인다.** 트랜스크립트는 맥락 없는 서브에이전트에게 범위를 잘라 넘기고 발견만 받는다.

```bash
T=$(find "$HOME/.claude/projects" -name "${CLAUDE_CODE_SESSION_ID:?세션 ID가 없다}.jsonl" -print -quit)
[ -n "$T" ] || { echo "트랜스크립트를 못 찾았다 — 건너뛰지 말고 원인부터 본다" >&2; exit 1; }
wc -l "$T"
```

**양쪽으로 죽어야 한다** — ID 미설정(`:?`)만 막으면 ID는 있는데 파일이 없을 때 `find`가 아무것도 안 찍고 exit 0으로 끝나, 회고가 "개입 없음"으로 조용히 넘어간다. **"가장 최근 파일"로 폴백하지 않는다** — 이 저장소는 작업마다 워크트리를 파고 세션이 동시에 여럿 돈다(issue-workflow 2단계). 최근 파일은 남의 세션일 확률이 높다.

~1500줄씩 겹치지 않게 잘라(`sed -n 'START,ENDp'`) 리더 에이전트에게 넘긴다. 리더에게는 **이번 세션이 무엇이었는지 한 문단과 자기 담당 범위만** 주고 **내 결론은 주지 않는다** — 중립이 목적이다.

- 리더가 "미완"이라 한 항목은 뒤쪽 범위와 **현재 파일 상태로 대조하고 나서** 올린다. 앞부분의 "아직 안 함"은 그 시점 관찰이지 세션의 결론이 아니다.
- **리더가 결과 없이 끝나면 반드시 재요청한다.** 서브에이전트가 응답 없이 idle로 끝나는 일이 있고, 그냥 넘어가면 그 범위의 발견을 통째로 잃는다.

## 2. 판정 — 규칙 코퍼스와 대조하는 건 별도 에이전트가 한다

수집 항목을 **기존 규칙 위반 / 규칙 공백 / 일회성** 세 통으로 나눈다. 이 판정은 리뷰 렌즈가 겸하지 않고 **회고 시점의 별도 에이전트**가 한다.

왜 리뷰가 겸하지 않나:

- 규칙 코퍼스는 루트 `.claude/rules/`와 `backend/.claude/rules/`·`frontend/.claude/rules/`, 그리고 각 영역 CLAUDE.md에 흩어져 있다. 버그를 찾는 렌즈마다 이걸 다 지고 "겸사겸사 어느 규칙인지 태깅"까지 시키면, 렌즈의 본업이 흐려지고 코퍼스가 늘 때마다 모든 렌즈가 같이 무거워진다.
- 위반은 리뷰 지적에만 있는 게 아니다. **재작업 커밋과 사용자 개입에도 있고, 그쪽이 더 아프다.** 리뷰가 태깅하면 리뷰가 본 것만 집계된다.
- 리뷰 시점에 박은 태그는 그때의 코퍼스에 고정된다. 회고 시점에 판정하면 **지금 있는 규칙**과 대조한다.

판정 에이전트에게 주는 것: 수집 항목 원문 + 규칙 파일 목록. **내 해석은 주지 않는다**(1-3과 같은 이유).

```bash
ls .claude/rules/*.md */.claude/rules/*.md */CLAUDE.md CLAUDE.md
```

받는 것 — 항목마다 하나:

| 통 | 뜻 | 다음 |
| --- | --- | --- |
| 기존 규칙 위반 | 규칙이 있는데 안 지켰다 | 문서를 고칠 게 아니다 → 3-1(도구로 내리기) |
| 규칙 공백 | 규칙이 없어서 놓쳤다 | 3번 사다리로 배치 |
| 일회성 | 이번에만 그랬다 | 버린다. 규칙으로 만들지 않는다 |

**"기존 규칙 위반"이 반복되면 그 규칙은 글이 부족한 게 아니라 도구가 없는 것이다.** 문장을 강하게 고쳐 쓰는 건 같은 실패를 한 번 더 하는 길이다.

## 3. 규칙을 추가하는 규칙

회고마다 규칙이 는다. 전역 `.claude/rules/`는 **항상 로드**돼서, 크기가 문제되기 전에 "다 읽었지만 몇 개는 안 지킴"이 먼저 온다 — 병목은 토큰이 아니라 주의력이다.

전역 `rules/`에 넣기 전에 아래를 순서대로 통과시킨다. **하나라도 걸리면 전역이 아니다.**

### 3-1. 기계로 강제되면 규칙이 아니라 도구다

lint·test·CI·훅·스킬로 어긴 걸 잡을 수 있으면 그리로 내린다. 도구는 주의력을 안 먹지만 문서에 적힌 규칙은 매번 사람이 읽고 지켜야 한다. 이미 그렇게 내려간 것: 이슈·PR·라벨 절차는 `/create-issue`·`/create-pr`, 리뷰는 `deep-review`, 경량/전체 경로 판별은 `scope.sh`(규칙이 직접 세지 않는다), 워크트리 env·포트는 `worktree-setup.sh`(#1660), 백엔드 정적 분석은 PMD(#1696).

기계로 못 잡는 **판단**만 규칙에 남는다 — "경계 애매하면 나누지 마라", "이 검증은 버그가 있을 때 실패하는가".

### 3-2. 경로 한정이면 전역이 아니다

백엔드 얘기면 `backend/.claude/rules/`, 프론트 얘기면 `frontend/.claude/rules/`. 그 폴더를 만질 때만 로드돼 필요할 때만 자리를 차지한다. 전역 `rules/`엔 **어느 영역을 만지든 참인 것**만 남긴다 — 지금 있는 git-push-safety·issue-workflow가 그 예다.

주의: 영역 경계를 넘는 규칙은 한쪽에 넣으면 다른 쪽을 만질 때 로드되지 않아 오히려 틀린다. 이런 건 전역이 맞다.

**스킬로 내릴 땐 그 스킬이 그 흐름의 발화로 실제 호출되는지부터 본다.** 절차를 옮겨도 `description`이 그 상황을 안 담으면 필요한 순간에 로드되지 않아, 아낀 게 아니라 잃은 것이다. 지시로 적기 전에 **한 번 불러 본다**.

### 3-3. 겪은 사고를 한 줄 교훈 + 이슈 링크로 적는다

규칙마다 실제로 데인 사건이 있어야 한다 — 없으면 추측이라 넣지 않는다("좋은 생각 같아서"는 입장 사유가 아니다). 사건은 **교훈 한 줄로 인라인**에 적고(그 문장만으로 "왜"가 서야 한다), 전말은 **그 사고를 고친 이슈/PR 번호로 링크**한다. 새 사건 문서를 따로 만들지 않는다 — 닫힌 이슈/PR이 이미 원천이다. 링크가 죽어도 인라인 문장 혼자 서야 한다.

지금 규칙이 지켜지는 건 다 구체 사고에 묶여서다 — #1404(`be/dev`가 PR 없이 직행), #1660(워크트리 env 누락으로 OAuth 없이 뜸), #1696(pmdTestFixtures 룰셋 누락으로 build 깨짐).

단 3-1·3-2·3-4처럼 **규칙에 관한 규칙**은 단일 사고가 아니라 코퍼스 전체의 반복 패턴에서 뽑은 것이라, 이 문단이 집합적 근거다.

### 3-4. 새 파일보다 기존 규칙 갱신

넣기 전에 겹치는 규칙부터 grep 한다. 같은 얘기를 두 곳에 적으면 둘이 어긋난다 — 갱신은 한쪽만 따라오기 때문이다.

### 3-5. 개수·열거를 문서에 박지 마라

파일 목록, 필드·상태값 열거, "현재 N개" 같은 수치는 코드가 바뀌면 문서만 낡는다. 판별하는 함수·스크립트가 있으면 목록 대신 그걸 가리킨다.

### 3-6. 저장소 규칙과 개인 memory를 가르는 선

| 어디 | 무엇 |
| --- | --- |
| `.claude/rules/`·`*/CLAUDE.md` | 누가 작업하든 참인 것. 팀이 공유하고 git에 남는다 |
| `~/.claude/projects/.../memory/` | 이 사용자·이 시점에만 참인 것 — 진행 중인 작업 상태, 개인 선호 |

**같은 교훈을 양쪽에 적지 않는다.** memory에 있던 게 팀 규칙으로 승격되면 memory 쪽은 지운다.

## 4. 덜어내기 — 넣을 때마다 뺄 것을 묻는다

규칙을 하나 넣을 때마다 "이번 작업에서 **한 번도 안 쓴** 규칙 중 지우거나 도구·스킬로 내릴 것이 있나"를 묻는다. 순증만 하면 주의력 병목으로 간다.

이번 작업에서 쓰인 규칙은 대화·PR 본문·리뷰에서 인용됐는지로 본다. 안 쓰였다고 곧 삭제는 아니다(스타일 규칙은 지켜도 언급이 없다) — **들여다볼 후보**를 고르는 용도다.

## 5. 확인 후 반영

반영할 항목과 강등·삭제 후보를 `AskUserQuestion`으로 확인받고 나서 파일을 고친다. 규칙 삭제는 특히 그렇다 — 안 쓴 이유가 "이번 작업이 그 영역이 아니어서"일 수 있다.

반영이 끝나면 **판정 결과를 PR에 코멘트 한 개로 남긴다.** 항목마다 어느 규칙이었는지 `[규칙: <파일>]`로 표기한다.

```bash
gh pr comment "$PR" --body "$(cat <<'EOF'
## 회고

- 위반 — WS 이벤트 추가 시 명세 갱신 누락 `[규칙: frontend/.claude/rules/websocket.md]` → 스킬로 내림
- 공백 — (없던 규칙) …
EOF
)"
```

지금은 사람이 읽는 기록이다. 이 표기가 몇 달 쌓이면 규칙별 위반 빈도를 집계할 수 있고, 그때 장부를 붙인다 — **데이터가 없는 상태에서 집계기부터 만들면 0만 찍힌다.**
