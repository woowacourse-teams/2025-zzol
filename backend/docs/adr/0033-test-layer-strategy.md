# 0033. 테스트 계층 전략 — 피라미드 유지와 계층별 책임 경계

- 날짜: 2026-07-05
- 상태: 승인 (규칙 명문화 진행 중, #1512)

## 컨텍스트

테스트 rule을 경계별(단위·서비스·통합)로 분리하면서(#1512), 각 경계 규칙에 "어떻게 쓰나"(네이밍·베이스 클래스·픽스처)는 있지만 **"어느 계층에서 무엇을 테스트하나"**는 어디에도 없다는 것이 드러났다. `docs/conventions-test.md`와 기존 테스트 ADR(0013 격리·0015 베이스·0016 픽스처·0017 web environment)은 전부 **인프라·구조**만 다루고, **전략(테스트 피라미드) 차원은 공백**이었다.

전략이 없어도 지금까지의 스위트는 우연히 건강한 편이다. 감사 결과 도메인 단위 테스트 약 586개 대 통합 테스트 38개로, 피라미드 밑변은 넓고 빠르다. 문제는 그 위다. `:game` 모듈의 통합 테스트가 다음과 같이 **비싼 풀스택 왕복 위에서 도메인 분기·완주 시나리오를 재검증**한다.

- **완주 드라이브**: `SpeedTouchGameIntegrationTest`는 DONE 프레임 하나를 보려고 50번의 실제 WebSocket 왕복을, `RacingGameIntegrationTest`는 약 6초의 실제 탭을 돌린다. "전원 완주 → DONE"은 이미 각 도메인 테스트(`SpeedTouchGameTest`, `RacingGameTest`)가 검증한다.
- **분기 매트릭스**: `BlockStackingIntegrationTest`는 무효 진행 이벤트 2개 분기를, `LadderIntegrationTest`는 index 경계·중복 요청을 풀스택으로 재검증한다. 모두 도메인/서비스 단위 테스트에 이미 있다.
- **라이브러리 검증**: `RedisContainerIntegrationTest`는 string/hash/set/transaction 등 8개 메서드로 Redis 클라이언트 라이브러리 동작 자체를 재확인한다(우리 코드가 아님).

이 재검증들이 `:game` 테스트 실행 시간 132초의 핵심 원인이며, 이는 상위가 비대해지는 **아이스크림콘 안티패턴**의 초기 신호다. 방치하면 통합 테스트가 계속 불어나 느려지고, 느려지면 팀이 통합 테스트를 불신·삭제해 콘이 굳는다.

또 하나 구조적 공백이 있다. 페이즈 전이(`DESCRIPTION→READY→PLAYING→DONE`, `earlyFinishDelay`·`hardCap`)를 **가짜 스케줄러로 즉시 검증하는 빠른 테스트가 Nunchi에만 있다**(`NunchiFlowOrchestratorTest`의 `CapturingScheduler`). 나머지 게임의 타이밍은 오직 실시간 `sleep`을 도는 통합 테스트로만 검증된다.

## 결정

**클래식 테스트 피라미드를 유지·명문화한다.** 케이스는 가능한 낮은 계층에서 소진하고, 통합 테스트는 얇게 유지한다.

핵심은 비율(70/20/10 같은 숫자)이 아니라 **휴리스틱**이다. 비율은 그 창시자들도 "모자에서 꺼낸 숫자"라고 인정하므로 KPI로 강제하지 않고 실루엣 점검용으로만 쓴다.

1. **도메인 분기 매트릭스는 domain/service에서 소진한다.** 순수 도메인 로직으로 판정되는 분기(스코어 정렬, overlap 경계, index 범위 등)는 하위 계층이 책임진다. 다만 **하나의 해피패스 플로우를 진행하다 자연스럽게 생길 수 있는 예외**(예: 블록쌓기에서 규칙대로 못 쌓는 입력이 들어와도 브로드캐스트되지 않고 게임이 계속되는지)는 그 플로우 검증의 일부로 확인한다 — 통합에 **별도 예외 매트릭스를 만드는 것이 아니라**, 한 플로우에서 실제 일어날 수 있는 예외 정도만 본다.
2. **플로우당 최소 1개의 현실적인 해피패스 시나리오는 끝까지 검증한다.** 상태 전이(예: `DESCRIPTION→READY→PLAYING→DONE`)와 WebSocket 브로드캐스트를 실제 흐름으로 관통하는 시나리오를 **유지**한다 — 인위적 near-terminal 주입은 기본이 아니라 예외적 수단이다. 다만 같은 종료를 보려고 수십 번의 왕복을 반복하지 않는다(필요 입력 수가 큰 게임은 테스트용으로 짧게 구성한다). 종료 조건의 순수 도메인 분기는 통합에서 다시 열거하지 않는다.
3. **페이즈/타이밍은 가짜 스케줄러로 오케스트레이터 계층에서 검증한다.** Nunchi의 `CapturingScheduler`(예약된 태스크를 즉시 실행)를 표준으로 삼고, 통합 테스트에서 실시간 `sleep`으로 타이밍을 검증하지 않는다.
4. **통합 테스트 = 유저 플로우당 현실적 해피패스 시나리오 1개 + 임계 와이어링 + 그 플로우 중 발생 가능한 예외.** 임계 와이어링은 우리 아키텍처가 강제하는 비동기 경로(Handler→Redis Stream→Consumer→Service→Notifier→broadcast)와 실제 MySQL 거동이다. 순수 도메인 결과 하나를 더 보려고 통합 테스트를 늘리는 것은 하위로 내리라는 신호이지만, **한 플로우를 진행하다 실제로 생길 수 있는 예외가 잘 처리되는지는 통합의 몫**이다.
5. **계층별 책임 경계**를 아래로 고정한다.

| 계층 | 테스트할 것 | 자제(내려보낼 것) |
|------|-------------|-------------------|
| 도메인(단위) | 비즈니스 로직·상태전이·스코어링·경계값·불변식. Spring 없이 `입력 x,y → 결과 z` | 트리비얼 getter/DTO, private 메서드, 프레임워크 동작 |
| 서비스/슬라이스 | 트랜잭션·조합·이벤트 발행·매핑·직렬화·쿼리. 외부는 목 | 단위로 되는 순수 로직 재검증 |
| 통합 | 현실적 해피패스 시나리오(상태 전이 관통)·Stream 비동기 왕복·실제 영속성·WS 왕복·그 플로우 중 발생 가능한 예외의 처리 | 도메인 분기 매트릭스 열거, 라이브러리/프레임워크 검증, 같은 종료를 위한 반복 왕복 |

6. **판단 규칙**: "이 케이스를 더 적은 컨텍스트로도 같은 이유로 실패시킬 수 있나?" → 예면 내린다. 상위 테스트가 빨간데 대응하는 하위 테스트가 없으면 하위 테스트가 누락된 것이다(작성한 뒤 상위 중복 여부를 판단한다).

7. **금지 안티패턴**: 계층 간 중복 커버리지, 통합 테스트의 비즈니스 분기 열거, 프레임워크·라이브러리 동작 검증, 과잉 목킹(도메인이 아니라 외부·경계만 목), 습관적 `@SpringBootTest`·`@DirtiesContext`.

## 고려한 대안

| 대안 | 장점 | 단점 |
|------|------|------|
| 클래식 피라미드 (채택) | 도메인 로직이 풍부한 백엔드에 정합. 빠른 밑변으로 대부분의 버그를 싸게 잡음. 기존 스위트 분포와 일치 | 통합이 얇아 "실사용 유사도"가 낮은 영역이 생김 → 임계 와이어링 통합으로 보완 필요 |
| 테스팅 트로피 (integration-heavy) | 조합·경계 버그를 실사용에 가깝게 검출 | Kent Dodds의 처방은 **프론트엔드용**. 우리 버그는 도메인 분기에 있어 전이 안 됨. 통합 비대 → 느림·flaky |
| 현상 유지 (전략 규칙 없음) | 당장 작업 없음 | 아이스크림콘 경향 방치, `:game` 132초 지속·악화, 판단 기준 부재 |
| 비율 KPI 강제 (70/20/10 게이트) | 수치로 명확 | 창시자도 자의적이라 인정한 숫자. 커버리지 게이밍·의미 없는 테스트 양산 유발 |

## 트레이드오프

- **신뢰도 일부를 속도·유지보수와 교환한다.** 통합 테스트를 줄이면 "실제로 함께 동작하는가"의 검증 표면이 좁아진다. 이를 임계 와이어링 통합(비동기 경로·실제 MySQL) 1개씩으로 방어하되, 완벽한 조합 커버리지는 포기한다.
- **push-down은 하위 테스트 누락 리스크를 동반한다.** "통합에서 빼라"만 지키고 하위 테스트를 안 쓰면 커버리지 구멍이 난다. 그래서 휴리스틱을 "빼라"가 아니라 "하위에 있는지 확인하고 없으면 쓴 뒤 뺀다"로 명시한다.
- **가짜 스케줄러(`CapturingScheduler`)는 실제 스케줄러 스레딩·지연을 검증하지 않는다.** 타이밍 "값" 계산과 전이 순서는 빠르게 검증하지만, 실제 `ThreadPoolTaskScheduler`의 동시성 거동은 커버하지 않는다. 그 부분은 스케줄러 자체를 신뢰(프레임워크)하고 통합 스모크 1개로 최종 확인한다.
- **일반론 일부를 의도적으로 거부한다.** 외부 베스트프랙티스는 "로컬 `testcontainers.reuse.enable=true` + 통합 테스트 병렬화 + 싱글턴 컨테이너"를 권하지만, 우리는 #1402에서 공유 컨테이너·병렬이 자원 경합으로 flaky함을 확인해 **JVM별 독립 컨테이너(reuse off)**로 결정했다. 이 ADR은 그 결정을 **뒤집지 않는다** — 계층 전략과 컨테이너 격리는 별개 축이다.

## 결과

- 이 전략은 `.claude/rules`의 경계별 오버레이(`testing-integration.md`·`testing-service.md`·`testing-domain.md`)와 공통 `testing.md`, 그리고 `docs/conventions-test.md`에 "테스트할 것/자제할 것"으로 명문화된다(후속 커밋).
- 감사에서 나온 과잉 통합 테스트(완주 드라이브·분기 매트릭스·라이브러리 검증)와 페이즈 타이밍 공백(`CapturingScheduler` 미적용 게임)은 **실증 리팩터로 분리**해 별도로 정리한다 — 이 ADR은 기준을 세우고, 리팩터는 그 기준을 적용한다.
- 기존 테스트 ADR과의 관계: 0013(격리)·0015(베이스)·0016(픽스처)·0017(web environment)은 **테스트를 어떻게 구성·격리하나**의 인프라 축이고, 본 ADR은 그 위에서 **무엇을 어느 계층에서 테스트하나**의 전략 축이다. 컨테이너 격리는 #1402를 그대로 따른다.
- Claude와 리뷰어는 통합 테스트 추가·리뷰 시 "이 케이스가 도메인/서비스로 내려갈 수 있는가"를 판단 기준으로 삼는다.
