# 0035. 시즌 정산 스트림에 Redis 컨슈머 그룹 도입 — 브로드캐스트와 작업 큐의 분리

- 날짜: 2026-07-24
- 상태: 승인 (구현 포함 — #1610)
- 참조: ADR-0022(리스너 시작 오프셋 — 대안 D에서 컨슈머 그룹 기각, 본 결정이 그 기각 조건을 뒤집는 첫 사례), ADR-0025(게임 결과 저장 리스너 — 정산 발행 훅 위치), ADR-0024(전역 식별 — 리더보드 노출 식별자), 이슈 #1610

## 컨텍스트

ZZOL의 모든 Redis Stream 소비는 standalone XREAD 브로드캐스트다. WebSocket 세션이 인스턴스 로컬이고 방 상태가 인메모리 복제라, 모든 인스턴스가 모든 이벤트를 소비해야 알림·상태 갱신이 성립한다. ADR-0022 대안 D는 이 전제 위에서 컨슈머 그룹을 기각했다 — 그룹의 분배 의미론이 브로드캐스트 요구와 충돌하고, 처리 보장은 프로듀서 측 Outbox가 담당하며, MAXLEN ~100이라 PEL 재전달의 실효도 없다는 논리였다.

미니게임 결과를 시즌 포인트·티어·리더보드로 정산하는 기능(#1610)은 이 전제를 처음으로 벗어난다. 정산 대상은 MySQL에 있는 **전역 단일 상태**라서, 브로드캐스트로 소비하면 blue/green 겹침 구간에 포인트가 이중 가산되어 오염된다. 필요한 것은 "전 인스턴스가 각자 반영"이 아니라 "**정확히 한 인스턴스가 한 번만 처리**"다.

기각 논리를 조건별로 다시 보면, 이 워크로드에서는 셋 다 뒤집힌다.

| ADR-0022 기각 조건 | 게임 이벤트(브로드캐스트) | 시즌 정산 |
|---|---|---|
| 분배가 브로드캐스트와 충돌 | 충돌한다 — 세션·상태가 인스턴스 로컬 | 충돌 없음 — 상태가 전역이라 분배가 목적 그 자체 |
| 보장은 Outbox(발행 측)로 충분 | 소비 유실 허용 | 소비까지 보장 필요 — 유실 = 포인트 누락 |
| MAXLEN 100이라 재전달 실효 없음 | 실시간 이벤트라 재생 무의미 | 보존을 늘리면 된다 — 정산은 나중에 해도 유효 |

## 결정

정산 전용 스트림 `settlement:result`를 만들고, ZZOL 최초의 XREADGROUP 소비 경로를 붙인다. 기존 브로드캐스트 스트림들은 그대로 둔다 — 같은 Redis Stream을 워크로드 특성에 따라 두 의미론으로 나눠 쓴다.

### 1. 스트림 등록과 브로드캐스트 리스너의 충돌 해소 — `listener-enabled`

`redis.stream.keys`에 키를 넣으면 `RedisStreamListenerStarter`가 브로드캐스트 리스너를 자동 생성하고, 넣지 않으면 `StreamPublisher`가 발행을 거부한다. `StreamConfig`에 `listener-enabled`(기본 true)를 추가해 이 충돌을 푼다. false인 스트림은 발행 경로만 열리고 리스너·소비 스레드풀·스레드풀 게이지를 만들지 않으며, 소비는 별도 컨슈머 그룹 소유 컴포넌트가 담당한다.

### 2. 보존 정책 분리 — MAXLEN 100 vs 10000

브로드캐스트 스트림은 유실 허용이라 MAXLEN ~100으로 밀어내지만, 정산 스트림은 처리 보장이 목적이라 10000으로 잡는다. 소비가 밀릴 때 미처리 메시지가 트리밍되면 PEL 항목이 남아 있어도 XCLAIM 회수가 빈 껍데기가 되어 보장이 깨지기 때문이다. "같은 기술인데 스트림마다 보존이 다른 이유"가 곧 두 의미론의 차이다.

### 3. 발행 — 결과 저장 트랜잭션 안에서 Outbox 경유

발행 훅은 `MiniGameResultSaveEventListener`(ADR-0025) 안이다. 게임별 종료 지점은 전부 스케줄러 스레드(트랜잭션 밖)라 Outbox를 끼울 수 없고, 결과 저장 트랜잭션을 가진 이 리스너가 유일한 훅 위치다. 게임 코드는 수정하지 않으며 대상 게임은 게이트(`SETTLEMENT_TARGET_GAMES`)로 제어한다 — BLIND_TIMER로 선행 검증한 뒤 같은 PR에서 전 게임으로 확장했다. 포인트가 방 안 등수 기반이라 게임 간 점수 단위가 달라도 성립하고, 등수 계산(`MiniGameResult.calculateRank`)은 전 게임 공통이며 동점은 같은 등수를 공유한다(1,1,3). 동점 포인트는 골프·F1 관례를 따라 동점 구간의 포인트를 합산해 균등 분배한다(리뷰 #1612 반영). 전원 동점 판은 각자 평균 포인트를 받게 되어 정상 플레이의 기대 포인트와 같아지므로 전원 실패 담합의 이득이 없고, 게임별 실패 판정 지식 없이 등수만으로 계산된다. 동점자 수 산정에는 게스트 포함 전체 순위 분포가 필요해 정산 이벤트에 allRanks를 싣는다.

정산 이벤트의 eventId는 랜덤 UUID가 아니라 `roomSessionId + miniGameType`에서 안정 파생한다. `MiniGameFinishedEvent.eventId()`는 인스턴스별 랜덤이라, blue/green 양쪽 발행·Outbox 재발행에서 같은 사건이 다른 ID를 갖게 되어 멱등 기준으로 쓸 수 없다.

### 4. 소비 — XREADGROUP + 수동 ACK + PEL 회수 + DLQ

- 그룹은 0-0부터 생성(MKSTREAM)한다. 그룹 생성 전 발행분도 처리 대상이다.
- 시작 오프셋은 그룹의 last-delivered-id(`ReadOffset.lastConsumed`)다. ADR-0022가 XREVRANGE로 해석하던 오프셋을 서버가 기억하므로 재시작 유실 창이 없다.
- 처리 성공 시에만 XACK한다. 일시 실패는 ACK 보류로 PEL에 남기고, 스위퍼가 유휴 60초를 넘긴 pending을 XCLAIM으로 회수해 재처리한다. XCLAIM이 전달 횟수를 올리므로 반복 실패는 MAX_DELIVERIES(5)에 도달해 DLQ(`settlement_dead_letter` 테이블)로 격리된다 — Outbox DEAD_LETTER와 같은 철학이며, 저장소도 같은 이유로 RDBMS다(리뷰 #1612: 격리 메시지는 장기 보존·사후 분석이 목적인데 Redis는 메모리를 점유하고 eviction으로 유실될 수 있다).
- 파싱 불가·타입 불일치(포이즌)는 재시도가 무의미하므로 즉시 DLQ + ACK한다.
- 그룹이 사라지면(AOF 없는 Redis 재시작 등) NOGROUP을 감지해 자가 재생성한다.
- 컨슈머 이름은 호스트명(dev-app-blue 등)이라 XPENDING에서 어느 인스턴스가 미ACK인지 바로 읽힌다.

### 5. 멱등성 — 원장 유니크 제약이 최종 방어선

at-least-once 전달을 전제로, 정산 원장 `season_settlement`의 `(room_session_id, mini_game_type, user_id)` 유니크 제약이 이중 지급을 DB에서 차단한다. 이미 정산된 결과는 조회로 건너뛰어 부분 정산 후 재전달도 이어서 처리되고, 조회를 빠져나간 동시 경합은 제약 위반을 전파해 재전달로 수렴시킨다. 포인트 가산은 DB 원자 UPDATE라 어느 지점에서 재실행돼도 결과가 부풀지 않는다. 시즌 키는 처리 시각이 아니라 이벤트 시각에서 파생해 시즌 경계를 넘긴 재처리도 같은 시즌으로 정산된다.

### 6. 알림 — 작업 큐에서 브로드캐스트로 복귀

정산 완료 후 순위 변동은 기존 브로드캐스트 스트림(minigame)으로 되돌려 보내 전 인스턴스가 로컬 세션에 뿌린다. 정산(단일 처리 경로 + 멱등)과 알림(전 인스턴스)이 각자 맞는 의미론을 타는 분기점이다. 알림은 **유실 허용**이다 — 정산 커밋 후 발행이 실패하면 재전달 시 정산이 스킵되어(settled 비어 있음) 그 알림은 다시 나가지 않는데, 토스트는 홈 화면 시즌 랭킹에서 언제든 확인 가능한 보조 채널이라 발행 상태 영속화 같은 재시도 장치는 두지 않는다. 리더보드 API의 노출 식별자는 ADR-0024의 `nickname#userCode`이고 userId는 노출하지 않으며, 표시 이름은 `:game`이 정의하고 `:user`가 구현하는 포트(ADR-0034 패턴)로 얻는다.

### 7. 관측 — XINFO GROUPS

브로드캐스트 스트림은 그룹이 없어 XLEN + 스레드풀 큐로 lag을 근사하지만, 정산 스트림은 `XINFO GROUPS`의 진짜 pending(전달 후 미ACK)·lag(미전달 backlog)·컨슈머 수를 게이지로 노출한다. DLQ 깊이는 settlement_dead_letter 테이블 count 게이지로 노출한다. 알림 룰은 배포 후 베이스라인 측정 뒤 추가한다(#1599 job 스코프 CI 체크 준수).

## 고려한 대안

- **대안 A. 브로드캐스트 + DB 유니크 제약**: 정합성은 지켜지지만 N-1개 인스턴스가 매번 헛수고하고, 정산이 단일 INSERT가 아니라 read-modify-write 여러 개(포인트·티어·연승)라 제약 하나로 끝나지 않는다. 기각.
- **대안 B. 브로드캐스트 + 분산 락**: 기존 `RedisLockAspect`로 가능하지만 락 경합만 만든다. "한 번만 배달"이 근본 해법인 문제를 "여러 번 배달 후 한 명만 통과"로 우회하는 셈. 기각.
- **대안 C. Outbox식 DB 폴링 워커**: 이미 있는 패턴(SKIP LOCKED)의 재사용이라 유력했다. 다만 폴링 지연이 있고 분배·재전달·pending 가시성을 전부 직접 구현해야 한다 — 컨슈머 그룹은 이것을 Redis가 제공한다. 기각(가장 아까운 대안).

## 트레이드오프

- **채택안의 비용**: 그룹·PEL·스위퍼·DLQ라는 새 운영 표면이 생긴다. blue/green 교체로 남는 유휴 컨슈머는 그룹에 계속 등록되어 있다(XPENDING 회수로 기능엔 지장 없으나 XINFO 노이즈 — 정리는 후속). 스위퍼의 `existsBy` 조회→처리 사이 경합은 유니크 제약이 막지만 예외 경로가 재전달을 한 번 더 태운다.
- **연승 계산의 순서 민감성 유예**: 컨슈머가 인스턴스당 1스레드라 같은 컨슈머 안에서는 도착 순서가 보존되지만, 두 인스턴스가 같은 회원의 결과를 나눠 받으면 순서가 어긋날 수 있다. 현재 정산은 순서 무관(가산)이라 문제없고, 연승 같은 순서 민감 파생값을 넣을 때 파티셔닝(회원별 라우팅)을 재검토한다.
- **리더보드 저장소**: 처음에는 Redis ZSET 파생 뷰로 만들었다가 리뷰(#1612)에서 SQL 조회로 회귀했다. 회원당 시즌 1행·저빈도 조회 규모에서는 파생 뷰가 주는 O(logN) 순위 조회 이득보다 DB와 어긋나는 창·조회 왕복·재구축 부재라는 비용이 크다. 순위 조회가 병목이 되는 규모(수만 회원·고빈도 조회)가 되면 ZSET 파생 뷰를 다시 검토한다 — 진실 공급원은 그때도 `season_score`다.
