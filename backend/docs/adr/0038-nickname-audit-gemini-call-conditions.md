# 0038. 닉네임 검열 Gemini 호출 조건을 골든셋 실측으로 정한다

- 날짜: 2026-11-10
- 상태: 승인 (#1909 리뷰 중)

## 컨텍스트

닉네임 AI 검열은 12시간마다 돌았다. 판정 전 닉네임을 랭킹에서 가리는 작업(#1906)이 들어가면 정상 사용자도 최대 12시간 동안 이름이 가려진다. 목표는 게임 한 판 길이인 5분이다(#1907).

주기를 줄이면 Gemini 호출이 늘어난다. 무료 등급의 병목은 분당 요청 수가 아니라 하루 요청 수다. 이 프로젝트의 `gemini-3.5-flash-lite` 무료 한도는 AI Studio에서 하루 500회로 확인했고, dev와 prod가 이 한도를 나눠 쓴다. 그래서 회차 주기, 호출 한 번에 싣는 건수, 실패한 호출을 다시 보내는 횟수가 모두 하루 호출 수를 정한다.

이전 결정은 측정 없이 정해졌다. [ADR-0001](0001-ai-nickname-audit-with-operator-feedback-loop.md)은 Gemini 2.5 Flash와 12시간 주기를 골랐고, 배치 크기 100은 근거가 기록되지 않았다. 골든셋 러너(#1828)가 생겨 모델과 배치 크기를 같은 입력으로 비교할 수 있게 됐다.

### 측정 조건

골든셋 579건(욕설 79, 우회 156, 경계 43, 정상 301)을 운영 프롬프트로 돌렸다. 모델은 `gemini-3.5-flash-lite`이고 피드백 예시는 넣지 않았다.

배치 크기별 1회 측정:

| 배치 | 호출 | 응답 평균/최대 | MISSING | 정상어 오탐 | 욕설 미탐 |
| --- | --- | --- | --- | --- | --- |
| 100 | 6 | 11.9s/14.2s | 0 | 2 | 0 |
| 150 | 4 | 19.5s/29.0s | 0 | 5 | 4 |
| 200 | 3 | 18.9s/21.5s | 0 | 0 | 0 |
| 300 | 2 | 35.3s/37.9s | 0 | 0 | 0 |
| 579 | 1 | 87.8s | 0 | 0 | 0 |

후보 배치 3회 반복:

| 배치 | 회차별 MISSING | 응답 평균/최대 | 오탐 | 미탐 | 판정 흔들림 |
| --- | --- | --- | --- | --- | --- |
| 200 | 1/1/0 | 24.3s/40.0s | 0 | 0 | 0.9% |
| 250 | 0/0/0 | 23.7s/48.6s | 0 | 0 | 1.2% |
| 300 | 0/0/0 | 35.5s/61.2s | 0 | 0 | 0.9% |

배치 150의 미탐 4건은 모두 '존나' 계열이고 판정 사유가 같았다. 한 회차 안의 흔들림으로 봤고, 3회 반복에서는 재현되지 않았다. 배치 200의 MISSING 1건은 모델이 'ㅊㅋㅊㅋ'를 바꿔 돌려준 응답 닉네임 불일치라서 배치 크기와 상관이 없다. 경계 43건의 PENDING은 모든 배치에서 0건이었다. 이 문제는 #1911 에서 다룬다.

## 결정

- **운영 모델을 `gemini-3.5-flash`에서 `gemini-3.5-flash-lite`로 바꾼다**(#1909). dev는 원래 flash-lite였으므로 두 환경이 같은 모델을 쓴다.
- **회차 주기는 prod 5분, dev 30분이다.** 미검열 닉네임이 없는 회차는 Gemini를 부르지 않는다. prod는 하루 최대 288회차, dev는 48회차다.
- **Gemini SDK의 내부 재시도를 끈다**(#1909). SDK는 설정이 없으면 408·429·5xx 응답에 같은 요청을 다섯 번까지 다시 보낸다. 켜 두면 장애가 난 날 288회가 1,440회까지 늘어 하루 한도를 넘는다. 실패한 호출은 행을 `UNAUDITED`로 남기고 다음 회차가 다시 집는다.
- **배치 크기를 100에서 250으로 올린다**(#1910). 579건을 호출 3회로 끝내고, 최대 응답 48.6초가 `request-timeout` 120초 대비 2.5배 여유를 둔다.

prod의 하루 호출 수는 `288 + 하루 닉네임 수 ÷ 250`을 넘지 않는다. dev 48회를 빼면 prod 몫은 452회라서, 하루 닉네임이 41,000건을 넘을 때 산수상 한도를 넘는다.

## 고려한 대안

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| 배치 300 | 579건을 호출 2회로 끝낸다 | 3회 반복 최대 응답이 61.2초라 타임아웃 여유가 2배로 준다 |
| 배치 579 단일 호출 | 호출 1회 | 응답 87.8초라 서버가 붐비면 120초 타임아웃을 넘길 수 있다 |
| 배치 200 | 오탐·미탐 0건, 최대 응답 40.0초 | 579건에 호출 3회로 250과 같고, 하루 처리 상한은 250보다 낮다 |
| `gemini-3.5-flash` 유지 | 판정 품질 변화가 없다 | 무료 한도를 확인하지 못했다. 3.5-flash 요청이 3.6-flash 한도에서 차감되는 것을 429 응답으로 확인해, 한도를 산수로 지킬 수 없었다 |
| `gemini-2.5-flash` | 무료 등급에서 쓸 수 있다 | 골든셋 정상어 오탐 14.3% |
| `gemini-3.1-flash-lite` | 무료 등급에서 쓸 수 있다 | 골든셋 정상어 오탐 5.0% |
| Gemma | 무료 한도가 넉넉하다 | `responseSchema`를 넣은 요청에 500을 돌려줘 구조화 응답을 받을 수 없다 |
| Valkey 카운터로 하루 호출 수를 세어 멈춘다 | 유입이 몰려도 한도를 넘지 않는다 | 한도를 서비스 로직이 아니라 주기 산수로 지키기로 #1909 리뷰에서 정했다. 지금 유입은 하루 수십 건이다 |

## 트레이드오프

- 한도를 넘기는 날을 막는 장치가 없다. 하루 닉네임이 41,000건을 넘으면 429가 나고, 행은 한도가 풀릴 때까지 `UNAUDITED`로 남는다. 그동안 회차마다 실패 요청이 계속 나간다.
- SDK 재시도를 껐으므로 일시적인 503 한 번에도 그 배치는 이번 회차에서 실패한다. 시도 횟수는 오르지 않고 5분 뒤 회차가 다시 집는다.
- 배치를 키우면 호출 하나가 실패할 때 판정이 미뤄지는 행도 250건으로 늘어난다.
- 판정 흔들림은 배치 250에서 1.2%로 200·300의 0.9%보다 조금 높다. 오탐·미탐으로 이어지지는 않았다.
- 측정은 골든셋 579건이 전부다. 운영 닉네임 분포가 골든셋과 다르면 이 수치가 그대로 맞지 않는다.

## 결과

- `backend/app/src/main/resources/config/service.yml`의 `nickname-audit` 블록이 모델, `batch-size: 250`, `cron`, `request-timeout`을 든다. dev 주기는 `application-dev.yml`이 30분으로 덮어쓴다.
- `NicknameAuditConfig`가 SDK의 HTTP 재시도 시도 횟수를 1로 고정한다.
- [ADR-0001](0001-ai-nickname-audit-with-operator-feedback-loop.md)의 모델·주기 결정을 이 ADR이 대체한다. 결과 분류와 피드백 루프 결정은 그대로다.
- [ADR-0018](0018-profanity-module-extraction.md)이 만든 `:profanity` 모듈 구조는 바뀌지 않는다. 이 ADR은 그 안의 검열 호출 설정만 정한다.

### 재검토 조건

- 골든셋 오탐이나 미탐이 0건에서 늘어나면 배치 크기와 모델을 다시 잰다.
- Gemini 무료 한도나 모델별 한도 차감 방식이 바뀌면 주기와 배치 크기를 다시 계산한다.
