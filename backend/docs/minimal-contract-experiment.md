# 최소 계약 실험 — 게임 AI 검증 파이프라인 설계 (초안)

> 상태: 팀 논의용 초안 (2026-08-27). 렌더링 버전은 세션 아티팩트로 공유.

규칙 문서를 걷어내고 카드게임을 새 아키텍처로 재구현시켜, 진짜 필요한 규칙·컨텍스트·테스트 케이스가 무엇인지 소거법으로 검증한다. 여러 에이전트의 후보 구현을 점수지로 채점해 최고안을 채택하는 best-of-N 파이프라인 제안.

## 1. 배경 — 이 실험이 답하려는 세 가지 질문

`.claude/` 규칙·스킬·CLAUDE.md에 쌓아온 컨벤션이 실제로 AI 행동을 바꾸는지 측정해본 적이 없다. 문서를 **주지 않은** 상태에서 게임을 재구현시켜 다음을 확인한다.

1. **규칙 문서 없이도 준수하는가?** — 없어도 지키는 규칙은 소거 후보, 없으니 어긴 규칙만 "진짜 필요했던 문서"로 생존한다.
2. **진짜 필요했던 컨텍스트는 무엇인가?** — 위반·실수를 역추적하면 필요한 문서 섹션이 문장 단위로 드러나고, 어떤 문서에도 없는 실수라면 문서화된 적 없는 암묵지의 발견이다.
3. **테스트해야 하는 케이스를 스스로 만들어냈는가?** — 기존 구현과 똑같을 필요 없이, 케이스 수준의 행동을 충족하고 그 케이스들을 스스로 발견하는지를 본다.

전제: 문서를 치워도 **코드베이스 자체가 컨벤션을 가르친다**(미니게임 7종). 따라서 측정하는 것은 문서의 절대 가치가 아니라 코드가 이미 보여주는 것 위에 문서가 더해주는 **한계 가치**다.

**프레임**: "문서 유/무 비교"가 아니라 **최소 계약 찾기**. 에이전트에게 주는 것은 게임 동작 스펙 + 원초적 규칙 초안(§3)뿐이고, 측정하는 것은 "이 최소 계약만으로 충분한가, 무엇이 더 필요했나"이다. 재구현은 새 아키텍처(§2)로의 개선 구현이므로 부산물이 그대로 기존 코드 개선의 입력이 된다.

## 2. 목표 아키텍처 — 외부 상태 + 상태 변경 후 이벤트 발행

현행 "메시지 처리는 반드시 Redis Stream 경유" 규칙의 근거를 분해하면, Stream의 실제 역할은 **상태 복제**다. 게임 상태가 인메모리라(ADR-0025), 컨슈머 그룹 없는 브로드캐스트 스트림으로 **전 인스턴스가 같은 명령을 소비해 각자의 인메모리 상태를 똑같이 전이시킨다**(복제 상태 머신). Notifier도 전 인스턴스가 호출하며, 그 중복 발행은 `WsRecoveryService`의 Lua 중복 제거(payload 기반 messageId — 같은 메시지는 첫 저장의 streamId 반환)가 걸러낸다. 직렬화는 스트림별 단일 스레드 풀 + `joinCode`별 `synchronized` 락이 담당하며, "Handler→Stream 필수" 규칙 자체는 자동 검사가 없다(ADR-0036, ArchUnit 후속 이슈로 미룸 — 문서로만 지켜지는 규칙의 대표 사례).

게임 상태를 Redis/DB로 외부화하면 라우팅 문제가 소멸한다. 아무 인스턴스나 명령을 받아 외부 상태를 원자적으로 전이시키고, 저장 성공 후 이벤트를 발행해 알림·영속·통계가 따라온다. 이벤트 발행은 이미 절반 존재한다 — `MiniGameFinishedEvent` 등 상태 변경 *이후* 구간은 지금도 in-process 동기 이벤트다(ADR-0025, `@Async` 금지). 이번 변경은 그 패턴을 **명령 수신 구간까지 앞으로 당기는 것**이다.

```text
현행:  Client →WS→ Handler →XADD→ Redis Stream →전체 방송→ 전 인스턴스가 소비, 각자 인메모리 상태 복제·전이
                                                          → 각 인스턴스 Notifier → /topic (복구 저장은 Lua dedup)
목표:  Client →WS→ Handler(아무 인스턴스) →직접 호출→ App Service →원자적 전이→ 외부 상태(Redis/DB)
                                                       └─ 저장 성공 후 → 이벤트 발행(동기) → Notifier → /topic
```

대상은 **카드게임**. 눈치게임의 300ms 충돌 윈도우 같은 극한 지연 요구가 없고(선택 시간이 초 단위), 규칙 개입 지점과 구현 비용의 균형이 좋다.

### 정합성 모델 — 진실은 저장소, 알림은 힌트

"pub/sub 유실이 나면 다른 인스턴스가 변경을 몰라 충돌하지 않는가"라는 우려는, 현행 구조에서 메시지가 하던 **세 역할을 분해**하면 해소된다.

| 역할 | 현행 (Stream) | 새 패턴에서의 운명 |
| --- | --- | --- |
| ① 명령 전달 | 전 인스턴스로 방송해 각자 상태를 복제 전이 | **소멸** — 도착한 인스턴스 하나가 공유 저장소를 직접 전이 |
| ② 인스턴스 간 정합성 | 이벤트 소비가 곧 인메모리 상태 복제 — 유실 = 상태 분기 = 충돌 | **저장소로 이관** — 다른 인스턴스는 필요할 때 저장소를 읽는다. 동시 전이 충돌은 R8이 **거부로 해소** — "충돌 허용"이 아니라 한쪽이 거부되고 최신 상태를 다시 읽어 재시도·거절 응답 |
| ③ 클라이언트 브로드캐스트 | 전 인스턴스가 소비 후 로컬 클라이언트에 `/topic` | **잔존** — 인스턴스 간 채널이 여전히 필요한 유일한 곳, 유실 우려가 실재하는 지점 |

③의 유실 평가에는 전제 교정이 필요하다. **현행 Stream 사용도 이미 유실을 허용한다** — 컨슈머 그룹 없음 + fromLatest라 재시작 구간 메시지는 지금도 유실되며 ADR-0022가 명시 수용("브로드캐스트 이벤트는 일시 유실 허용, fromStart 리플레이는 기능이 아니라 가려진 버그"). 유실 불가 경로(정산·결과 영속)는 Outbox + 컨슈머 그룹(ADR-0035)이 따로 담당한다. Stream이 pub/sub보다 실제로 나은 것은 연결 유지 중 잠깐 밀려도 마지막 오프셋부터 이어 읽는다는 것 하나다. 새 패턴은 "유실 불가 = Outbox / 알림 = 유실 허용" 원칙을 계승한다.

**정합성 모델 3원칙**:

1. **진실은 외부 저장소에만 있다** — 상태 전이는 저장소에서 원자적으로(R8), 충돌은 거부로 해소된다.
2. **알림은 상태를 나르지 않는다** — 나르더라도 진실이 아니다. 알림 유실의 최악 결과는 일시적으로 낡은 화면이지 상태 손상이 아니다.
3. **유실은 재동기화로 치유한다** — 알림에 단조 증가 버전을 실어, 수신 측이 버전 갭을 감지하거나 재연결하면 저장소에서 스냅샷을 다시 읽는다(R12).

이 모델 위에서 브로드캐스트 채널이 pub/sub이든 Stream(알림 전용)이든 정합성에는 영향이 없고, 남는 차이는 "낡은 화면이 얼마나 자주·오래 생기나"라는 UX 등급뿐이다. 계약에는 R12 원칙만 고정하고 **채널 선택은 후보 자유** — 어떤 채널을 왜 골랐는지 자체가 설계 비교 데이터가 된다.

### 클라이언트 정합의 구체화 — 스냅샷 발행과 자연 치유

"클라이언트가 이벤트를 못 받으면 불일치, 발행 실패 시 현재 상태로 정합 처리 필요"라는 우려의 답은 기존 컨트랙트에 이미 절반 있다. **현행 카드게임 컨트랙트는 스냅샷 방식이다** — `CardGameNotifier`가 카드 선택·단계 완료마다 `/topic/room/{joinCode}/gameState`로 `MiniGameStateMessage.from(cardGame)`(게임 상태 전체)를 브로드캐스트한다. 델타가 아니므로 유실된 메시지는 다음 브로드캐스트가 자동 치유한다. 이를 R12의 구체 규칙으로 승격한다:

- **발행 규칙** — 상태 페이로드는 전이 시점의 메모리 값이 아니라 **저장소에서 읽은 최신 전체 스냅샷**. 어떤 알림이든 도착만 하면 클라이언트가 완전 정합
- **발행 실패** — 재시도를 요구하지 않는다(제공 채널 어댑터에도 재시도가 없다). 스냅샷 방식이므로 다음 발행이 자연 치유하며, 실패가 상태를 해치지 않아야 한다는 것이 계약의 전부다
- **정지 구간**(마지막 메시지 유실 후 이벤트 없음)이 잔여 위험 — 재연결·재구독 시 현재 스냅샷 재전송 경로를 **기존 컨트랙트 범위 안에서** 후보가 설계 (FE 수정 금지, §5 제약)

## 3. 원초적 규칙 초안 — 패턴이 바뀌어도 살아남는 것

루브릭은 2티어: 패턴 불변인 **원초적 규칙**은 계약으로 공개·채점하고, Stream 종속 규칙은 소멸·치환한다. 이 분류 자체가 첫 산출물이다 — 어떤 조항이 아키텍처 종속이고 어떤 조항이 본질인지 처음으로 명문화된다.

### 불변 — 계약에 포함, 채점 대상

| ID | 규칙 | 근거 |
| --- | --- | --- |
| R1 | **동시성 직렬화** — 게임 단위 상태 변경은 직렬화. 입력과 타이머 콜백이 다른 스레드에서 같은 상태를 만진다. Stream을 빼면 입력 간 직렬화까지 전담하므로 더 중요해짐 | NunchiFlowOrchestrator 락 주석 |
| R2 | **모듈 의존 방향** — `:room` ↛ `:game`, `:common` Spring 무의존 | ArchUnit 강제 |

| R4 | **이벤트 계약** — record + `BaseEvent`, 불변 DTO, 도메인 객체 노출 금지, in-process 동기(`@Async` 금지), 추적 코드 미포함 | ADR-0021 · 0025 |

### 외부 저장이 신설하는 규칙 (Stream이 공짜로 주던 것의 승계)

| ID | 규칙 |
| --- | --- |
| R8 | **원자적 상태 전이** — 읽기–수정–쓰기 race 방지 (Redis Lua/WATCH, DB 락/버전 — 수단은 자유, 부재는 위반) |
| R9 | **저장 성공 후 발행** — 이벤트는 상태 저장 성공 뒤에만. 뒤집히면 구독자가 낡은 상태를 봄. R12와 짝(R9 발행 측, R12 수신 측) |
| R10 | **핸들러 멱등성** — 재시도·중복 명령이 상태를 이중 전이시키지 않아야 함 |
| R11 | **핫패스 지연 예산** — 게임 루프 안 동기 접근은 Redis까지만, DB는 정산·영속 경로만 |
| R12 | **알림은 진실이 아니다** — 상태 알림은 저장소에서 읽은 최신 전체 스냅샷으로 발행(전이 시점 메모리 값 금지). 발행 실패는 재시도 불요(다음 발행이 자연 치유), 정지 구간은 재연결·재구독 시 스냅샷 재전송으로 재동기화(§2). 채널(pub/sub·Stream)은 자유 — 이 규칙만 지키면 됨 |

## 4. 동시성·저장소 방식 — 결정하지 않고 대결시킨다

외부 상태 패턴의 1차 설계 결정은 **"상태를 어디에 두고, 동시 전이를 무엇으로 직렬화하는가"**다. 복잡도·성능·테스트 용이성을 전부 좌우하고, Lua 스크립트 복잡도 우려 같은 실감나는 리스크가 여기서 나온다. 이걸 관점 축으로 삼는다.

| 관점 | 직렬화 수단 | 강점 | 약점·리스크 |
| --- | --- | --- | --- |
| **A. MySQL 단일 진실** | 상태를 MySQL 행으로, JPA `@Version` 낙관 락 (비관은 후보 판단) | 인프라 최단순, 트랜잭션·롤백 공짜. 카드게임은 입력 빈도가 낮고 초 단위라 **"Redis가 정답인가"의 반증 시도**로 성립 | 왕복 지연 상대적으로 큼, 커넥션 풀 경합 |
| **B. Redis 낙관** | 버전 CAS — 제네릭 Lua 1개("버전 일치 시 값+버전 교체") 또는 WATCH/MULTI. **게임 규칙은 전부 Java 도메인에** | 지연 최소. Lua를 원자 교환 프리미티브로만 쓰면 복잡도가 거의 안 오름 | 도메인 로직을 Lua로 옮기는 함정(규칙 명세 R8 경고) — 빠지면 복잡도 폭발 + R7 충돌 |
| **C. Redis 분산 락** | 기존 `@RedisLock`(RedisLockAspect) 재사용, 락 안 read-modify-write | **리포에 이미 있는 인프라 재사용**, 사고 모델 최직관 | 락 왕복 지연, 락 만료·해제 실패 엣지 케이스 |
| **D. 현행 Stream 유지** | 상태를 외부화하지 않고 현행 복제 상태 머신 그대로 — 스트림별 단일 스레드 풀 + `joinCode`별 `synchronized` 락. 그 위에서 재구현·개선 | **코드가 패턴을 가르치는 대조군**(나머지 미니게임 6종이 Stream 패턴을 코드로 보여준다), 전환 비용 0, 기존 인프라(Stream·Lua dedup·복구) 그대로 | 인메모리 상태·인스턴스 라우팅 책임이 그대로 남음, 타이머 소유권 문제 미해결 |

**타이머 — 대결 종료, 원칙 고정**: 타이머 소유권은 저장소 선택에 종속되는 2차 결정이라 축에서 내렸다. 공통 원칙으로 고정한다 — **"페이즈 마감 시각을 저장소에 두고, 폴링 claim으로 발화한다"**(구현은 저장소에 맞게: Redis ZSET / DB 데드라인 컬럼 폴링). 마감이 저장소에 있으므로 어느 인스턴스가 죽어도 타이머가 유실되지 않는다. 이 원칙은 외부 저장 관점(A/B/C)에만 적용된다 — D는 현행 타이머 방식을 유지하며, 중복 발화 없음은 스켈레톤 `같은_페이즈_마감은_두_번_발화되지_않는다`로 전 관점 공통 증명한다. *기록: 당초 타이머 소유권 3안(리스/폴러/중복 발화+클레임)을 대결시키려 했고 sticky 라우팅은 외부 프록시 전제로 제외했는데, 폴러 원칙 고정으로 대결 자체가 불필요해졌다.*

**결정 방식**: 스펙에는 **"멀티 인스턴스(임의 라우팅)에서 동작"**만 못박고, 네 관점(A/B/C/D)을 후보 에이전트에 배정한다 — **4관점×2회 총 8개 후보**로 관점 간 차이와 관점 내 변동성을 함께 본다. D는 실험 질문 1·2("문서 없이도 지키는가")의 가장 순수한 대조군이다 — A/B/C가 코드가 패턴을 가르쳐주지 않는 새 아키텍처에서 문서의 한계 가치를 재는 반면, D는 나머지 미니게임 6종이 Stream 패턴을 코드로 보여주는 상태에서 문서만 뺀 조건이라, **Tier 2 페어와이즈에서 D가 A/B/C를 이기면 "아키텍처 전환 근거 없음"이 곧 실험 결론**이 된다. 같은 행동 케이스로 채점, Tier 2 비교에서 설계끼리 붙인다. 채택 기록이 상태 저장소·동시성 ADR 초안이 된다.

## 5. best-of-N 파이프라인

```text
샌드박스 베이스 브랜치 ──┬─▶ 후보 A×2 (MySQL 낙관)       ─┐
(카드게임 제거+계약 주입) ├─▶ 후보 B×2 (Redis CAS)        ─┤
                        ├─▶ 후보 C×2 (Redis 분산 락)    ─┼─▶ Tier 0 자가 게이트 ─▶ 오케스트레이터 채점 ─▶ 상위 후보 draft PR
                        └─▶ 후보 D×2 (현행 Stream 유지) ─┘   (빌드·테스트·ArchUnit·     (Tier 1·2, 채점표 비공개)  (점수 근거 첨부)
                                                              lint·컨트랙트 diff)
```

**SCOPE 제약**: **BE 한정 + 기존 API 컨트랙트 고정.** 재구현은 백엔드만 하며, 기존 WS 토픽·REST 엔드포인트·페이로드를 그대로 유지해 **FE가 무수정으로 동작**해야 한다. 이 제약으로 컨트랙트 준수가 결정적 게이트가 되고(`@WsTopic` 카탈로그 diff), 행동 채점의 기준면도 고정된다.

1. **샌드박스 베이스 준비(1회)** — dev에서 분기해 ① 카드게임 구현 패키지·테스트·factory 등록·스트림 키 제거 — 단 **와이어 계약에 속한 열거값·봉투는 유지**한다(`MiniGameType.CARD_GAME`, `CommandType.SELECT_CARD`, 명령 레코드). REST 응답과 명령 봉투가 이 값들을 나르므로 지우면 컨트랙트 자체가 깨진다 ② **문서 제거**: `.claude/`·CLAUDE.md 3종 + `backend/docs/`의 컨벤션·ADR·실험 문서 전부(케이스 체크리스트 `minimal-contract-cases.md` 포함 — 남으면 문서 ablation과 케이스 비공개가 둘 다 오염된다) ③ 계약 2종만 주입 — 동작 스펙([minimal-contract-spec.md](minimal-contract-spec.md), 와이어 컨트랙트 포함) + 규칙 명세서 ④ **공용 인프라 주입** — 알림 채널 경계 SPI + pub/sub 어댑터(traceparent 전파 포함)를 신규 제공하고, Stream 채널은 기존 경계(`StreamPublisher`)가 이미 전파를 제공하므로 그대로 재사용(ADR-0021 경계 패턴 일반화). 원칙: **관점 축이 아닌 횡단 관심사(트레이싱)는 공용화**해 실험 변수를 오염시키지 않고, R4("이벤트에 추적 코드 금지")의 전제를 채널 무관하게 유지한다 ⑤ **동결 인수 테스트 스위트(공개) 주입** — 동결된 컨트랙트(WS/REST)만으로 검증하는 E2E 스위트: 핵심 해피패스(상태 시퀀스·선택·조기 전환)뿐 아니라 **기존 테스트가 못 챙긴 예외까지** — 실패 케이스(비정상 상태 선택, 중복 카드, 잘못된 인덱스, 비방장 시작), 동시성 케이스(동시 선택 경합, 중복 명령). **수정·삭제 금지, 전부 통과 필수**(무변경은 diff로 기계 검사). 나머지 6개 게임은 유지 — "코드가 가르치는" 조건은 실전과 동일하게 ⑥ **규칙 증명 스켈레톤(`experiment/sandbox/inject/`) 주입** — 그 트리를 그대로 복사해 `game/src/test/java/coffeeshout/cardgame/proof/CardGameRuleProofTest.java`를 심는다. 메서드명 8개만 있고 본문은 `fail("TODO ...")`이며, 후보가 자기 아키텍처에 맞게 채운다. 메서드명이 아키텍처 중립이라 A/B/C/D 전 관점에 같은 파일을 준다.
2. **후보 구현(8개 병렬)** — 관점 4개 × 관점당 2회. **후보 작업 공간은 샌드박스 브랜치의 single-branch shallow clone(depth 1)** — 다른 브랜치·과거 히스토리(삭제된 카드게임 포함)가 물리적으로 존재하지 않아 답지 접근이 불가능하고, 원격 조회(`git fetch` 등)는 권한 설정으로 차단한다. 계약 문서의 실험 수칙(샌드박스 격리) 위반 시도는 실격. 스펙에 구현 힌트(구조·네이밍·위치) 금지. "추측·막힘·필요했던 정보를 `ASSUMPTIONS.md`에 기록"을 프롬프트에 포함(컨텍스트 수요 자기 보고).
3. **Tier 0 자가 게이트** — 빌드·자작 테스트·**제공 인수 스위트 무변경 통과**·ArchUnit·lint·**컨트랙트 동일성(`@WsTopic` 카탈로그 diff = 0)**·**규칙 증명 스켈레톤 8건**(무삭제 — 주입 원본과의 diff에서 시그니처·어노테이션 줄에 `-`가 있으면 실패, `@Disabled` 추가 금지 · 전부 채움 — `fail("TODO` 잔존 시 실패 · 본문마다 assertion/verify 최소 1개 · 8건 전부 통과). 결정적 검사만이라 구현 에이전트에게 공개해도 안전하고, 통과까지 스스로 고친다.
4. **오케스트레이터 채점** — Tier 1·2. 판정 에이전트는 구현 세션과 컨텍스트를 공유하지 않는다. *구현 에이전트가 검증을 직접 호출하면 비공개 채점표가 구현 컨텍스트로 새기 때문.*
5. **상위 후보 draft PR** — 점수 리포트(항목별 판정 + 근거 파일:줄)를 본문에 첨부, 사람이 최종 확인. merge는 언제나 사람 몫.

## 6. 점수지 — 3티어 채점

채택이 목적이면 점수는 **선발 도구**다. LLM 채점의 함정(절대 점수 압축, 장황함에 후함, 순서 편향)을 구조로 막는다. 원칙: **LLM에게 절대 점수를 매기게 하지 말고, 항목 판정과 상대 비교만 시킨다.** 점수는 판정에서 계산으로 도출.

- **Tier 0 — 게이트 (점수 아님)**: 빌드 · 자작 테스트 · **제공 인수 스위트 무변경 통과** · ArchUnit(R2) · lint/style · 컨트랙트 동일성(`@WsTopic` 카탈로그 diff = 0). 실패 시 채점 자체를 안 함.
- **Tier 1 — 절대 채점**: 후보별 독립, 항목별 `충족/위반/해당없음` + **근거(파일:줄)** 강제. 근거 없는 판정 폐기(deep-review 원칙). **근거 검증 랩(환각 방지)** — 위반 판정은 2단 검증을 통과해야 집계: ① 존재 검증(script — 인용 파일·줄·문구 실재 확인) ② 지지 검증(저비용 에이전트 — 근거 한 건만 보고 "이 코드가 이 주장을 지지하는가: 예/아니오/불명"). 존재 실패·'아니오'는 폐기, '불명'만 재질의. 가중: 행동 충족 **최대** > 원초적 규칙(관점별 규칙 세트 — A/B/C는 R1–R12, D는 R1–R7·R10·R12 + S1–S3) **중** = 테스트 품질(케이스 재현율 + 신규 유효 케이스 가점) **중**. **규칙 점수는 관점별 규칙 세트에 대한 충족 비율로 정규화**해(`해당없음`은 모수에서 제외) 규칙 수가 달라도 관점 간 비교가 성립하게 한다. **행동 충족 판정은 4단**: ① 공개 인수 스위트는 Tier 0 게이트에서 기계 검증 완료 ② **비공개 홀드아웃 스위트**(케이스 체크리스트의 실행 가능판 — 오케스트레이터가 채점 시 실행, 후보에게 미노출) ③ **규칙 증명 스켈레톤**(`CardGameRuleProofTest` 8건 — 존재·통과는 Tier 0에서 script가 이미 검증했고, Tier 1에서는 "본문이 메서드명이 주장하는 성질을 실제로 검증하는가"를 좁은 llm이 예/아니오 + 근거 줄로 판정한다. 근거 검증 랩을 그대로 재사용) ④ 실행 불가한 잔여 케이스는 **판정 방향을 반전**한다 — "케이스마다 코드를 찾아라"가 아니라 **"후보가 쓴 테스트를 하나씩 읽고 C01~C26 중 어디를 덮는지 분류하라"**. 케이스→코드 방향은 놓쳐도 티가 안 나지만 테스트→케이스 방향은 모든 테스트가 한 번씩 읽히고, 출력이 **26개 ID 전부를 필수 필드로 갖는 JSON**(건너뜀이 구조적으로 불가)이라 누락이 드러난다. 재현율은 이 분류 결과로 집계한다. 공개 스위트·스켈레톤에 노출된 케이스는 재현율 모수에서 제외한다(후보가 이미 봤으므로).
- **Tier 2 — 페어와이즈 (상위 2~3개)**: 설계 품질만 상대 비교 — 단순성 · 도메인 표현력 · 이벤트 계약 품질. 후보 익명화 + A–B/B–A 양방향 2회로 순서 편향 상쇄.

### 공개 범위 — Goodhart 방지선

| 산출물 | 구현 에이전트에게 | 이유 |
| --- | --- | --- |
| 동작 스펙 + 원초적 규칙 | 공개 | 지키라고 만든 계약 |
| Tier 0 게이트 목록 | 공개 | 결정적이라 게이밍 여지 없음, 자가 수정에 필요 |
| 규칙 증명 스켈레톤(메서드명·Javadoc) | 공개 | 증명 대상 규칙은 계약에 이미 공개돼 있고, 스켈레톤이 덮는 N케이스는 재현율 모수 밖 |
| 케이스 체크리스트 | 비공개 | 주면 이름만 맞춘 껍데기 테스트가 나옴. 감춰야 "스스로 만들어냈는가"가 측정됨 |
| 가중치 · 판정 프롬프트 | 비공개 | 선발 기준 게이밍 방지 |

채택 사유는 근거로 남긴다 — "후보 B 채택: 행동 케이스 17/19, 규칙 위반 1건(파일:줄), 페어와이즈 단순성 우세"가 PR 본문에 실린다.

## 7. 데이터 환류 — 실험이 끝나면 남는 것

best-of-N 한 번이 곧 실험 N회분이다.

**규칙 4분면** (위반 분포로 문서의 운명 결정):

| | 계약 없이도 지킴 | 계약 없으면 어김 |
| --- | --- | --- |
| **계약에 있으면 지킴** | 삭제 후보 — 코드가 이미 가르침 | 가치 입증 — 문서로 남길 이유 |
| **계약에 있어도 어김** | 측정 노이즈 | 기계화 대상 — 글로는 안 먹힌다, lint·hook·ArchUnit으로 |

- **컨텍스트 갭 목록** — 위반 역추적 + ASSUMPTIONS.md 취합. 기존 문서 섹션 매핑 = 필요성 입증, 매핑 불가 = 암묵지 발견(신규 문서 후보). `game-test-mirror.md`류의 "코드만 봐서는 못 배우는 함정"이 드러날 것으로 예상.
- **ADR 초안** — 동시성·저장소 방식 대결(§4)의 채택 기록.
- **코드 개선 백로그** — 채택 구현 vs 기존 구현 비교 리뷰(더 단순한 구조, 기존 스위트에 없던 케이스, 기존 버그).
- **점수지 개선** — 판정이 흔들린 항목의 루브릭 문장 보정. 회차를 거듭하면 점수지가 규칙 문서의 후계자가 된다.

## 8. 미결 사항과 다음 단계

**결정된 것**: 범위 = BE 한정 + 기존 API 컨트랙트 고정(FE 무수정 동작) · 관점 축 = 동시성·저장소 방식(MySQL 낙관 / Redis CAS / Redis 분산 락 / 현행 Stream 유지) × 각 2회 = 후보 8 · 타이머 = "저장소 데드라인 + 폴링 claim" 공통 원칙 고정(A/B/C — D는 현행 유지) · 알림 채널 = R12 원칙만 고정하고 후보 자유.
