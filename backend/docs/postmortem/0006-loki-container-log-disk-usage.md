# 0006. Loki 컨테이너 로그가 17G까지 쌓여 공유 호스트 디스크가 85%를 넘음

- 날짜: 2026-11-04
- 심각도: P1
- 상태: 완료

## 요약

2026-11-04 공유 호스트의 디스크 사용률이 85%를 넘어 `DiskUsageHigh` 알림이 #신고-알림 채널에 세 번 왔다. 원인은 Loki 컨테이너의 stdout 로그 파일 하나가 17.2G까지 커진 것이었다. Docker 기본 로그 드라이버인 json-file에는 크기 제한이 없고, 이 호스트의 어느 compose에도 로그 제한이 걸려 있지 않았다. 로그 내용은 에러가 아니라 Loki가 info 레벨로 남기는 인덱스 동기화 메시지였다. 사용자 영향은 없었다. 로그 파일을 비워 사용률을 49%로 내렸고, #1892에서 모니터링 컨테이너 8개에 로그 로테이션을 걸었다. 이 호스트에는 prod·dev 앱과 모니터링이 함께 있어서, 디스크가 꽉 찼다면 운영 서비스까지 쓰기에 실패했을 것이다.

## 임팩트

- 사용자 영향은 없다. 알림이 경고 단계에서 왔고 디스크는 6.6G가 남아 있었다.
- 실제로 넘쳤다면 영향 범위가 컸다. 알림 규칙 주석대로 90% 근처부터 쓰기 실패가 날 수 있고, 같은 디스크를 prod·dev 앱과 MySQL·Redis가 함께 쓴다.
- #1892 배포 때 모니터링 컨테이너가 재생성되면서 지표 수집과 알림이 1분 남짓 비었다.

## 근본 원인

**이 호스트의 어떤 컨테이너에도 로그 크기 제한이 없었다.**

1. **Docker 기본값이 무제한이다.** json-file 드라이버는 `max-size`를 주지 않으면 파일을 끝없이 키운다. 호스트에는 `/etc/docker/daemon.json`이 없었고, `monitor`·`prod`·`dev` compose 어디에도 `logging:` 블록이 없었다. 확인했을 때 모든 컨테이너의 `LogConfig.Config`가 `{}`였다.
2. **Loki가 가장 많이 쓰는 컨테이너였다.** Loki 2.9.6은 `log_level`을 정하지 않으면 info로 돈다. 인덱스 테이블 핸드오버와 index set 동기화 메시지가 주기적으로 찍혀 약 4개월 반 만에 17.2G가 됐다. 하루 130MB 정도다. 두 번째로 큰 grafana 로그는 0.7G였다.
3. **천천히 차서 눈에 띄지 않았다.** 사용률은 하루 0.3%p 정도씩 올랐다. 85% 경고 하나만 있어서 처음 알게 된 시점이 이미 여유 6.6G였다.

### ZzolBot 분석이 원인을 짚지 못한 이유

세 알림 모두 분석이 "ERROR 로그를 찾지 못해 알림을 뒷받침할 근거가 없다"로 생략됐다. `MonitorAnalysis.noEvidence`는 조회 구간에 ERROR 로그가 없으면 LLM을 부르지 않는다. 앱 에러 알림에는 맞는 판단이다. 하지만 디스크 사용률은 에러 없이도 오르는 지표라 ERROR 로그는 근거가 될 수 없다. 이번 원인도 에러가 아니라 info 로그의 양이었다. 같은 생략은 2026-09-03·09-16의 `RedisStreamBacklogHigh` 알림에도 붙어 있었다. 지표 기반 인프라 알림에서는 이 분석이 매번 비어서 나온다.

## 대응

- `df`와 `du`로 `/var/lib/docker/containers`를 좁혀 들어가 컨테이너별 로그 크기를 비교했다. Docker 이미지·볼륨·빌드 캐시는 회수 가능한 양이 0.4G 남짓이라 원인에서 뺐다.
- Loki 컨테이너 로그를 `truncate -s 0`으로 비웠다. 파일을 지우지 않고 크기만 0으로 만들어 Loki를 재시작하지 않았다.
- #1892에서 `backend/docker/monitoring/docker-compose.yml`에 공통 로그 설정을 두고 서비스 8개에 붙였다. 컨테이너 하나의 로그는 300MB를 넘지 않는다. `edge-cd`가 compose를 반영하면서 컨테이너를 재생성했고, 그때 grafana의 옛 로그 0.7G도 함께 지워졌다.

## 재발 방지 액션

| 액션 | 상태 |
|------|------|
| 모니터링 컨테이너 8개에 `max-size: 100m`, `max-file: 3` 적용 (#1892). 배포 뒤 `docker inspect`로 확인 | ☑ |
| prod·dev 앱 compose에 같은 로그 제한을 건다. 앱 로그는 지금 10MB 안팎이라 급하지 않다 | ☐ |
| 호스트 `/etc/docker/daemon.json`에 기본 로그 제한을, journald에 `SystemMaxUse`를 둔다. 저널이 3.1G다. 호스트 설정이라 GitOps 배포 경로가 없어 수동으로 하고 절차를 남긴다 | ☐ |
| ZzolBot이 지표 기반 인프라 알림에서 ERROR 로그 대신 다른 근거를 보게 하거나, 생략 사유를 "이 알림은 로그로 분석하지 않는다"로 바꾼다 | ☐ |

## 교훈

- **Docker 로그는 기본값이 무제한이다.** 컨테이너를 새로 올릴 때 `logging:`이 있는지 본다. 없으면 가장 말 많은 컨테이너가 언젠가 디스크를 채운다.
- **에러가 없다고 문제가 없는 것은 아니다.** 디스크를 채운 것은 info 로그였다. 지표 알림의 원인은 로그 레벨이 아니라 양과 위치로 찾는다.
- **분석 생략 메시지도 신호다.** 같은 "근거 없음"이 특정 알림 종류에 반복해서 붙으면, 알림이 아니라 분석 방식이 그 알림에 맞지 않는다는 뜻이다.
