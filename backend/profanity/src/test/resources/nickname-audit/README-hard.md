# 닉네임 검열 하드 골든셋

`golden-hard.csv` 는 검열 모델이 틀리기 쉬운 닉네임만 모은 350건이다. 모델을 고를 때 `golden.csv` 로는 차이가 드러나지 않는 구간을 보려고 만들었다(#1907).

`golden.csv` 579건은 회귀 기준이라 그대로 둔다. 두 세트는 원문도 `TextNormalizer` 정규화 결과도 겹치지 않는다.

## 돌리는 법

```bash
cd backend
NICKNAME_GOLDEN_SET=hard GEMINI_API_KEY=... ./gradlew :profanity:goldenTest
```

`NICKNAME_GOLDEN_SET` 을 비우면 `golden.csv` 를 읽는다. 리포트는 `profanity/build/reports/golden/{시각}-{세트}-{모델}-b{배치}.md` 로 남는다.

## 만든 방법

1. 탐색 에이전트(`.claude/agents/nickname-goldenset-explorer.md`)를 축을 나눠 여섯 번 돌려 후보 473건을 모았다.
2. 원문이나 정규화 결과가 `golden.csv` 또는 다른 후보와 겹치는 17건을 버려 456건을 남겼다.
3. 456건의 순서를 섞고 닉네임만 남겨 두 라벨링 에이전트에 따로 줬다. 두 실행은 모델이 다르고, 탐색 에이전트의 추정 라벨과 축 이름, 상대의 결과를 보지 못한다.
4. 두 라벨이 같으면 그 값을 `expected` 로 삼았다. 갈린 25건은 `AMBIGUOUS` 로 뒀다.
5. 목표 건수에 맞춰 우회 축은 축마다 18건, 하드네거티브는 106건, 애매는 34건까지 고정 시드로 무작위 표집했다.

라벨이 탐색 에이전트의 추정과 달라졌을 때 `category` 는 아래처럼 맞췄다.

- 두 라벨이 모두 `CLEAN` 이면 `하드네거티브` 로 옮긴다. 우회 축에 일부러 섞은 정상 닉네임과, 애매로 냈지만 둘 다 정상으로 본 닉네임이 여기에 든다.
- 하드네거티브로 냈는데 라벨이 갈린 닉네임은 `애매` 로 옮긴다.
- 애매로 냈는데 둘 다 `PROFANE` 으로 본 6건은 뜻에 맞는 유해 표현 축으로 옮긴다.
- 유해 표현 축에서 `AMBIGUOUS` 가 된 닉네임은 축을 그대로 둔다. 그래서 집단비하 28건 가운데 23건이 `AMBIGUOUS` 다.

버린 후보는 106건이다. 표집으로 104건, 맞는 축이 없는 직접 욕설 1건, 정규화하면 정답 조각이 2자 미만이 되는 1건이다.

갈린 25건은 모두 한쪽이 `AMBIGUOUS` 이거나 차단과 정상으로 갈린 경우다. `PROFANE` 과 `EVASION` 사이에서 갈린 건은 없다.

## 알려진 한계

- 라벨을 단 것은 사람이 아니라 언어 모델 두 번이다. 두 모델은 같은 계열이라 같은 방향으로 틀릴 수 있고, κ 0.92 는 사람 두 명의 일치도보다 높게 나왔을 가능성이 크다. 운영자가 표본을 뽑아 다시 보기 전에는 정답이 아니라 기준안으로 읽는다.
- 표본도 언어 모델이 만들었다. 실제 가입 닉네임의 분포를 따르지 않고, 모델이 떠올리지 못하는 최신 은어는 빠져 있다.
- 평가 대상인 Gemini 와 표본을 만든 모델이 아는 우회 수법이 비슷하면 이 세트가 실제보다 쉽게 나온다.
- 혐오차별과 집단비하는 일치율이 73.1%로 낮다. 이 두 축의 `AMBIGUOUS` 32건은 서비스 정책이 정해지면 다시 갈라야 한다.
- 우회 축은 축마다 18건이라 한두 건 차이로 축별 재현율이 5%포인트 넘게 움직인다. 축별 수치는 모델 사이의 큰 차이를 볼 때만 쓴다.
- 닮은꼴문자 가운데 NFKC 로 풀리지 않는 한자와 키릴 문자는 정규화 뒤에도 원래 문자로 남는다. 정답 조각 비교도 그 문자 그대로 한다.
- 실존 인물의 실명과 별명은 넣지 않았다. 인물 비하는 이 세트로 잴 수 없다.
